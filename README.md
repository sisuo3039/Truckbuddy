# Truckbuddy: Talk-to-Rule transportation demo

A voice demo for transportation administrators and drivers. The same deterministic functions can run directly inside ElevenLabs hosted **Code tools** or through the included HTTP MCP server.

The original fictional rule catalogue from `demoRuleDefinitions.js` is preserved in `data/rule-definitions.ts`. Despite its original extension, that supplied file contains TypeScript interfaces.

All stock, drivers, routes, traffic and weather are **fictional**, from a fixed **2026-10-15, Europe/Berlin** snapshot. There is no live provider or transportation-system connection.

## What the demo does

- Looks up all eight original rules with source, lifecycle, exceptions and catalogue inconsistencies.
- Helps an agent ask about mandatory requirements versus preferences, scope, conditions, thresholds/units, exceptions and time-window binding.
- Returns a structured rule draft and validation report for administrator review.
- Gives drivers stock availability after reservations/quarantine, exact per-stop quantities, bins, weight, pallet positions and load order.
- Combines vehicle/resource availability, stops, delivery windows, traffic/weather scenario delays, shift availability and dispatch blockers.
- Personalizes the driver with configurable `driver_name`, defaulting to **Vidhi**, and begins with an offer of a short morning briefing.
- Provides 17 additional mock operations for dairy loading, temperatures, permits, road restrictions, rest, delivery, weather and confirmed simulated route selection.

Rule drafts are returned in the conversation, not stored in a durable admin system. The tools cannot publish rules, reserve stock, change routes, cancel freight orders or authorize dispatch.

## Hosted in ElevenLabs

ElevenLabs MCP integrations connect to external server URLs. Enterprise Code tools can execute this mock JavaScript on ElevenLabs infrastructure, so an external host is unnecessary for the hosted demo.

Two hosted dispatchers use an `action` parameter: `truckbuddy_transport_mock` selects one of the original 12 operations, and `truckbuddy_vidhi_mock` selects one of the 17 personalized operations. Source, input definitions and agent prompt are prepared locally and tested before installation. Remote resource IDs and verification state belong in a checkout-local `elevenlabs/deployment.json`, which is excluded from Git. Copy [elevenlabs/deployment.example.json](elevenlabs/deployment.example.json) when setting up your own workspace.

The **Truckbuddy — Talk-to-Rule Demo** was installed and updated through ElevenLabs MCP. Both hosted dispatcher sources matched the tested local bundles. The saved prompt, variable greeting, Vidhi default and attached tools were verified. Contributors should create their own demo agent or obtain access to a shared ElevenLabs workspace.

A real hosted execution/voice conversation has not been tested: the available MCP connector exposes no text-only code execution API. Local function tests and actual HTTP MCP calls passed. Open the demo agent in ElevenLabs to try the phrases below.

## Try the demo

The personalized greeting is:

> Good morning, Vidhi. Would you like your morning briefing?

The first message is rendered at build time from `driver_name` so an unresolved placeholder never reaches that saved greeting. Change the default in `elevenlabs/dynamic-variables.json`, rebuild, and apply the generated greeting and personalized tool to change the opening name. Native session names still work in the prompt and tool context, with a configured-name fallback.

Spoken dialogue uses operational wording without fixture labels. The agent already knows the configured user, provides a short briefing when asked, and then retrieves the requested details. Try:

- “Yes, give me my morning briefing.”
- “What's the load breakdown?”
- “What temperature should the dairy stay at?”
- “Will I arrive in time?”
- “Show the road ahead.”
- “Any traffic updates?”
- “Is B441 suitable for my truck?” followed by an explicit “Confirm B441.”
- “The sensor hasn't updated.”

[docs/demo-script.md](docs/demo-script.md) is the presenter-ready runbook, with spoken lines, scene cues, optional branches and recovery prompts. [docs/vidhi-scenes.md](docs/vidhi-scenes.md) covers the scenario and variable configuration. The original driver and administrator scenarios remain available:

- “I’m Alex Morgan, driver D-001. What do I pick and load before my run?”
- “I’m Jamie Chen, driver D-002. Can I start my day?”
- “I’m Sam Rivera, driver D-003. Check my load and cross-dock arrival.”
- “For North Market on weekdays, deliveries must arrive before ten. Help me turn that into a rule.”
- “Show me the backload policy. Is it already approved?”

| Scenario | Expected outcome |
| --- | --- |
| D-001 / Alex Morgan | 476 cases, 10 pallet positions, 4,928 kg before packaging; 25 minutes of scenario delay; ready for dispatch review, not approved dispatch |
| D-002 / Jamie Chen | 30 produce cases short; first contractual stop 15 minutes late; dispatch blocked |
| D-003 / Sam Rivera | Planned load 75 kg over capacity; hub arrival 12 minutes after the buffered cutoff; dispatch blocked |

## Portable HTTP MCP

Requires Node.js 22 or newer.

```sh
npm install
npm run build
npm start
```

Local endpoint: `http://127.0.0.1:8787/mcp`

Health endpoint: `http://127.0.0.1:8787/health`

This stateless Streamable HTTP MCP server serves JSON responses. It listens on loopback by default. Set `PORT`/`HOST` for another deployment and `MOCK_MCP_TOKEN` to require bearer authentication. This local server is an alternative transport; the hosted ElevenLabs demo does not depend on keeping it running.

| Operation | Main input |
| --- | --- |
| `truckbuddy_demo_info` | None |
| `list_transport_rules` | Optional `query`, `stage`, `limit`, `offset` |
| `get_transport_rule` | `rule_id` |
| `prepare_rule_draft` | `spoken_requirement`, optional `draft_fields_json` |
| `validate_rule_draft` | `draft_json` |
| `get_stock` | Optional `warehouse_id`, `sku`, `date` |
| `get_resource_availability` | Optional `date` |
| `get_loading_plan` | `driver_id`, optional `date` |
| `get_driver_route` | `driver_id`, optional `date` |
| `get_traffic` | `corridor`, optional `date` |
| `get_weather` | `region`, optional `date` |
| `get_driver_day_briefing` | `driver_id`, optional `date` |

Only the fixed mock date is supported. Missing required IDs, unknown stock/regions, malformed JSON, invalid pagination and unsupported dates return actionable errors.

The HTTP MCP server exposes **29 operations** in total. The personalized operation names and argument schemas are in [src/vidhi-tool-definitions.mjs](src/vidhi-tool-definitions.mjs). All accept an optional `driver_name` and scripted `scene`; route-related lookups also accept `route_choice`. `vidhi_confirm_reroute` requires an explicit boolean `user_confirmed` and rejects the unsafe low bridge.

## Verification

```sh
npm run build
npm test
npm run check:mcp
```

Tests cover quantities, stock accounting, overload, late windows, cross-dock buffers, draft clarification, units, personalized names, stale sensors, clearance, confirmation and equivalence of both hosted JavaScript bundles. The MCP check uses the official SDK client against a temporary local HTTP server to verify handshake, tools/list, real tool calls, structured results, authentication and errors.

[docs/evaluation.xml](docs/evaluation.xml) contains fixed-snapshot questions for checking an agent's tool selection and interpretation. It is a manual evaluation set, separate from automated tests.

## Demo limits

For the original three drivers, traffic/weather delays are added once to each baseline stop ETA, pallets are counted per stop/SKU without mixing deliveries, and loading weights exclude packaging. Vidhi's separate dairy manifest includes a fixed 25 kg of packaging per pallet.

Vidhi's baseline arrives at 12:35, 25 minutes before the 13:00 window opens. The 45-minute accident delay produces 13:20, still within the 14:30 deadline. B441's seeded estimate preserves 12:35 and the rest stop; this is a fixture, not a live routing calculation.

Scenes advance through explicit requests or external demo events. No live GPS, geofence, sensor monitoring or automatic alerts are connected. Confirmed reroutes return a conversation receipt; they do not persist a route or update navigation. Configured shifts and rests are fictional values, not jurisdiction-specific working-time compliance. This is not an optimizer or a complete policy conflict checker.

The original rule catalogue deliberately remains unchanged. R-002's tolerance never permits physical overload; R-003's shipment example has an arithmetic error; R-006's condition text omits its 20-minute buffer; R-007 needs mandatory/preferred clarification; R-008 remains unpublished. These issues are visible in tool results.
